# Owner Intent (Owner-guided)

> ไฟล์นี้คือ **Source of Truth** สำหรับวิธีทำงานแบบ Owner-guided ของโปรเจกต์นี้ (Layer 0, ขั้นตอน High level/Guards/Data Dictionary/Coverage และข้อห้าม)  
> กฎการปฏิบัติการ/รูปแบบการสั่งงาน/Permission ให้ยึด `GLPT-Workreport/Playbook.md` เป็นหลัก

## ประโยคเดียวที่ Codex ต้องยึด

“หน้าที่ของฉันคือทำให้ Owner เห็นภาพรวมและช่องว่าง ไม่ใช่ตัดสินแทน Owner”

---

สรุปขั้นตอนและข้อมูลสำหรับ Codex (Owner-guided)
บทบาทของ Codex

Codex ไม่ใช่คนตัดสินใจแทนระบบ
Codex ทำหน้าที่ “แยก แปลง จัดรูป และชี้ช่องว่าง”
การตัดสินใจสุดท้ายเป็นของ Owner

Anti-Gravity ปล่อยให้พัฒนาโค้ดไป
Codex ทำหน้าที่คุม ความครบ + ความหมาย + ความเสี่ยง

Layer สำคัญที่สุด (ต้องอ่านก่อนอย่างอื่น)
Layer 0 – Business & System Behavior (ห้ามหาย)

สิ่งเหล่านี้ ไม่ถูก rewrite เป็นเทคนิค และต้องถูกอ้างอิงทุกขั้น

งานวิเคราะห์ย้อนหลัง ต้องไม่บล็อกงานประจำวัน

ช้าได้เฉพาะคนที่กดรายงานหนัก

ระบบต้องไปต่อได้แม้ข้อมูลบางฟิลด์ “ไม่เคยมีมาก่อน”

ผู้ใช้ต้องเห็น feedback ทุกครั้ง (ห้ามหน้าจอเงียบ)

UI คือจุดตัดสินว่าระบบ “ครบหรือไม่ครบ”

ขบวนการหลัก (ทำทีละเมนู / ทีละการ์ด)
ขั้นที่ 0: Requirement (ภาษาผู้ใช้)

อ่าน requirement เต็ม

ห้ามตัดเรื่องพฤติกรรมระบบ

เน้น “การใช้งานจริง + ความกังวลเชิงธุรกิจ”

ขั้นที่ 1: High Level (ภาษาคน ไม่ใช่เทคนิค)

Codex ต้องสรุป:

เมนูนี้มีไว้เพื่ออะไร

ผู้ใช้กดอะไร → คาดหวังเห็นอะไร

flow หลัก 3–6 ขั้น (ไม่พูด API / DB)

ถ้าอ่านแล้ว Owner ยัง “รู้สึกไม่ครบ” = ยังไม่ผ่าน

ขั้นที่ 2: Guards (Experience / System Rules)

Codex ต้องแยกกติกาออกมาเป็นข้อ ๆ เช่น:

กดแล้วต้องมี feedback

งานหนักห้ามค้างทั้งระบบ

ข้อมูลขาดได้ แต่ห้าม block flow

UI ต้องแสดงสถานะชัดเจน

Guards คือสิ่งที่ป้องกัน requirement หายตอนเป็นเทคนิค

ขั้นที่ 3: Data Dictionary (เชิง UI / Business)

Codex ต้องทำเป็นตาราง:

ฟิลด์ที่ UI ใช้จริง

ความหมายภาษาคน

ใช้แสดง/คำนวณตรงไหน

❌ ห้ามพูด PK / FK / schema
✅ เน้น “ข้อมูลนี้มีไว้ทำอะไรในสายตาผู้ใช้”

ข้อมูลแทน (Representative / Test Data)
เป้าหมาย

ใช้ทดสอบ UI

ใช้ทดสอบ performance

ใช้ทดสอบการวิเคราะห์รายวัน/สัปดาห์/เดือน/ย้อนหลัง

ไม่ใช่ migration

การใช้ข้อมูลเก่า

ใช้ข้อมูลจริงแค่ 1 เดือนก็พอ

จำนวนรวมประมาณ 30,000–50,000 แถว (หรือขยายด้วย rule)

ฟิลด์ไม่ครบไม่เป็นปัญหา

Coverage / Calibration Table (หัวใจของงานนี้)

Codex ต้องวิเคราะห์แล้วส่งออกเป็น ตาราง (CSV/XLSX) ให้ Owner ไปเปิดใน Google Sheets / Excel

ตารางต้องมีคอลัมน์อย่างน้อย:

Table

Field (New System)

Status: OK / PARTIAL / MISSING / NEW CAPTURE

Source Rule Type:

OWNER FILL

SIMPLE MAPPING

DERIVED

NEW CAPTURE

Legacy Source (ถ้ามี)

Rule / Notes

Owner Action (ปล่อยว่างให้ Owner กรอก)

หน้าที่ Codex = ชี้ช่องว่าง
หน้าที่ Owner = เติมและตัดสินใจ

หลักการ “ไม่เคยมีมาก่อน”

ถ้าฟิลด์/ตารางใหม่ ระบบเก่าไม่เคยมี:

ติดสถานะ NEW CAPTURE

ไม่ต้องคำนวณ

ไม่ต้อง fabricate

ระบบต้องไปต่อได้ (optional / default / แสดงสถานะ)

UI (สิ่งที่ Owner ใช้ตรวจว่าระบบครบหรือไม่)
Wireframe

เป็นภาพโครง

HTML + CSS ได้

❌ ไม่มี JS

ใช้ดูว่า “หน้านี้มีอะไรให้กรอก”

Card UI (จุดตัดสินจริง)

กดแล้วเห็นผล

ตารางมีข้อมูลแทนสมจริง

สถานะเปลี่ยน

modal / ปุ่ม / feedback ชัด

ถ้า UI ดูแปลก → แปลว่า requirement บางอย่างหาย

Performance & Risk (เชิงธุรกิจ)

Codex ต้องไม่ออกแบบอะไรที่:

รายงานย้อนหลังทำให้ทั้งระบบช้า

ดึงข้อมูลทั้งหมดมาทีเดียว

ผูกงานหนักกับงานประจำวัน

หลักคิด:

งานประจำวันต้อง “ไม่รู้สึกช้า”

งานวิเคราะห์หนัก ช้าได้เฉพาะคนที่กด

สิ่งที่ Codex ห้ามทำ ในรอบนี้

❌ สร้าง backend / API

❌ สร้าง schema / ERD

❌ บังคับ required field จากข้อมูลเก่า

❌ optimize เชิงเทคนิคก่อน UI ผ่าน

Definition of Done (สำหรับ Owner)

งานถือว่าผ่านเมื่อ:

Owner อ่าน High level + Guards แล้ว “รู้สึกครบ”

UI แสดงแล้วเห็นปัญหาจริง ไม่ใช่ภาพสวย

Coverage table ทำให้รู้ว่าฟิลด์ไหนต้องเติม

ระบบ “ไปต่อได้” แม้ข้อมูลบางอย่างไม่มี

ประโยคเดียวที่ Codex ต้องยึด

“หน้าที่ของฉันคือทำให้ Owner เห็นภาพรวมและช่องว่าง
ไม่ใช่ตัดสินแทน Owner”
